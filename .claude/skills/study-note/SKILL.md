# Study Note — 개인 학습 노트 작성

대상 저장소: **study_dev repo** — 이 머신에서는 `~/projects/study_dev` (다른 머신에서는 clone 위치. repo 안에서 실행 중이면 현재 repo가 대상). 노트는 루트에 평평하게, 탐색은 `INDEX.md` 하나로.

## ⚠️ 내용 경계 먼저 (개인 repo — 회사 자산 반입 금지)

- 회사 소스코드 원문 발췌, 내부 URL·호스트명, 시크릿, 고객/환자 데이터, 미공개 제품 정보를 넣지 않는다.
- 회사 일에서 출발한 주제는 **일반화**한다 — 회사 코드 대신 최소 재현 예제(일반 Spring/Kotlin/HTTP 등), 실제 도메인명 대신 중립 예시. 계기가 된 사건의 개요·티켓 키 언급 수준은 허용(사용자 판단).
- 위 경계에 걸리는 내용이 필요해 보이면 넣지 말고 사용자에게 알린다.

## 1. 쓰기 전에 — 카테고리부터

- **INDEX.md를 먼저 읽는다.** 탐색 단위는 카테고리다(예: 네트워크·실시간 통신 / 웹 보안 / 인프라 / 전송 계층 기초). 새 내용이 기존 카테고리에 속하면 **새 파일보다 기존 문서에 섹션 추가**가 기본이고, 어느 쪽인지 애매하면 사용자에게 확인한다.
- **규모 확장 규칙**: 카테고리는 한 파일의 섹션으로 시작 → 쌓이면 독립 파일로 분리 → 파일이 여럿이면 폴더로 승격. 분리·승격은 사용자가 원할 때만 하고, 하면 INDEX 링크를 함께 옮긴다.
- 파일명: 주제 기준 `<주제-슬러그>.md` — 티켓 키를 파일명에 쓰지 않는다(계기는 문서 머리에 한 줄로).
- 소재가 대화·코드 분석에서 왔으면, 노트에 옮기기 전에 사실 단언(프로토콜 동작·기본값·버전 의존)을 공식 문서 기준으로 확인한다 — 전역 "Verify, don't assert" 규칙 적용.

## 2. 가독성 기준 (표본: study_dev의 realtime-web-networking-cors-infra.md)

1. **독자 = 배경 지식 없는 나**. 약어·전문용어는 첫 등장에서 바로 푼다 — 약어는 원어+뜻(예: "XHR(XMLHttpRequest — JS에서 HTTP 요청을 보내는 브라우저 API)"). 뒤 섹션은 앞 섹션만 전제한다.
2. **이해 단계 건너뛰기 금지** — "당연히", "널리 알려진 대로"로 넘어가지 않는다. 중간 단계가 길어지면 본문 흐름을 끊지 말고 부록으로 뺀 뒤 링크한다.
3. **도입부**: 제목(서술형 — "~로 배우는 ~") / 무엇을 왜 배우나 2~3줄 / 작성일. 사건 기반이면 도입 직후 **사건 한 문단 요약** + "이 문단에 모르는 단어가 있으면 이 문서가 도움이 된다" 프레임.
4. **질문 → 섹션 표** (요약 바로 다음): 이 공부를 시작하게 한 실제 질문들을 그대로 적고 앵커 링크로 해당 섹션에 연결한다. 나중에 다시 열었을 때의 진입점이다.
5. **본문은 기초 → 심화 순서**로 쌓는다. 헤딩은 서술형(예: "왜 사내망에서 WebSocket이 막히나") — 목차만 읽어도 스토리가 보이게.
6. 개념마다 **"왜 이게 실전에서 중요한가"**를 짧게 연결한다(일반화된 사건 서술로).
7. 프로토콜·와이어 포맷은 실제 주고받는 바이트/헤더 예시로 보여준다. 표·목록 우선.
8. **`§` 기호를 쓰지 않는다** — 섹션·조항 참조는 `3장`, `4.7절`처럼 한글로 쓴다(INDEX 링크 텍스트 포함).

## 3. 마무리

- **INDEX.md 갱신 필수**: 해당 카테고리 밑에 항목(주제 — 문서의 섹션 앵커 링크)을 추가하고, 하단 문서 표의 작성/갱신 날짜를 맞춘다. 새 카테고리가 필요하면 만든다. INDEX 없이 노트만 두지 않는다.
- **링크 실재 확인**: INDEX와 본문의 앵커·상대 링크가 실제 헤딩·파일과 일치하는지 확인한다.
- 커밋·푸시는 하지 않는다 — 커밋 메시지 한 줄만 제안한다.
- 분량 기준 없음: 이해에 필요한 만큼 길게, 대신 위 구조(질문 표·부록)로 탐색 가능하게.
